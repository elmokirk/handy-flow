## Design

Ein Export verlässt die App und schreibt in ein Dateisystem, das jemand
anderem gehört. Genau deshalb müssen zwei Fragen **allein aus der Datenbank**
beantwortbar sein:

1. *Haben wir das schon gemacht?* → `idempotency_key` = Target + Item +
   Content-Hash. Gleiches Vault, gleiches Item, gleiche Bytes: **ein** Job,
   für immer. Ändert sich der Inhalt, ändert sich der Key — Updates fließen
   weiter. Der Hash steckt deshalb **im Schlüssel** und nicht in einem
   separaten „dirty"-Flag, das jemand zurücksetzen müsste.
2. *Was haben wir angefangen und nie beendet?* → Ein Job wird **nie
   gelöscht**. Ein Absturz hinterlässt ihn `running`; `requeue_stale_running`
   holt ihn zurück. Aufgebrauchte Retries parken ihn als
   `failed_permanent` — weiterhin abfragbar. Es gibt keinen Pfad, auf dem
   ein Export leise verschwindet.

Migration **V12** (`TARGET_VERSION` 11 → 12): `export_targets`,
`export_jobs`. `status` spiegelt exakt den eingefrorenen Zustandsautomaten
aus [[orchestration/DATA_STATE_MACHINES|DATA_STATE_MACHINES]] —
`pending → running → succeeded | retry_wait | failed_permanent`, plus
`retry_wait → running` — als DB-`CHECK`.

## Notes
- **Claim ist atomar.** Kandidatenauswahl und `UPDATE ... status='running'`
  laufen in einer Transaktion (Fixture 03). Zwei Worker, die dieselbe Datei
  schreiben, würden sie zerstören.
- **Backoff wächst deterministisch**: 30s, 60s, 120s, 240s. Kein Jitter —
  eine Einzelplatz-Desktop-App hat keine Thundering Herd zu entzerren, und
  Determinismus hält das Verhalten testbar (Fixture 04).
- **Ein Crash kostet kein Attempt.** `requeue_stale_running` erhöht den
  Zähler bewusst nicht: dass unser Prozess stirbt, ist kein Beleg dafür,
  dass der Export scheitern würde. Sonst verbrennt unser eigener Bug das
  Retry-Budget des Nutzers (Fixture 07).
- **`MAX_ATTEMPTS = 5` ist eine Obergrenze, kein Wegwerfen.** Eine
  unbegrenzte Retry-Schleife versteckt ein kaputtes Vault, statt es
  sichtbar zu machen. `failed_permanent` bleibt stehen und ist über
  `failed_permanent()` abfragbar — KB-404 kann es anzeigen.
- **Zwei Targets sind unabhängig** (Fixture 09): dasselbe Item in zwei
  Vaults sind zwei Jobs. Ein Target wird über *worauf es zeigt* identifiziert
  (`UNIQUE (kind, root_path)`), damit ein erneutes Registrieren desselben
  Vaults den Outbox nicht gabelt (Fixture 10).
