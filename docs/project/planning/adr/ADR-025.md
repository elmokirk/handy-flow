# ADR-025 — One checkpointed final WAV for live recording

## Decision

For new live dictations, create one original WAV directly in the normal
recordings directory at recording start. The recorder consumer checkpoints
the WAV header and syncs data every 30 seconds and on normal stop. The
capture exists before inference. Processing windows are in-memory views of
the original, not separate WAV files. Preserve the file on transcription
failure; deletion remains an explicit user operation.

## Why

The former live path saved audio concurrently with inference and inserted
the capture afterwards. A native model crash left a valid orphan WAV that
was invisible in the app. The user explicitly rejected replacing the
original with temporary audio chunks and chose a single growing original.

## Contract change and limits

This supersedes the `temp → atomic rename` lifecycle in
`planning/04-DATA_PERSISTENCE.md` and AUDIO-104 **for new live dictation**.
Wispr imports and other file ingestion may retain their separate atomic
copy/finalize paths. At most the audio since the last completed sync may be
at risk during sudden power loss; a disk or OS can still fail. An incomplete
final WAV is never silently deleted: startup recovery reports or repairs it
without changing PCM bytes where safe. Capture transcription state remains
derived from attempts per ADR-024.

## Owner authorization

Kirk approved direct-to-original recording, 30-second checkpoints,
visible failure/recovery, manual CPU fallback, and no delayed auto-paste in
the 2026-09-23 long-audio remediation conversation.
