# PAD-306 — Canonical capture/attempt pipeline in the live transcription path

[[planning/tickets/INDEX|← Ticket Index]] · [[planning/phases/PHASE-4|Phase 4]]

**Owner:** Integrator
**Dependencies:** [[planning/tickets/DATA-105|DATA-105]], [[planning/tickets/PAD-305|PAD-305]]
**Allowed ownership:** `transcript capture/attempt write path`

**Origin:** [[escalations/PAD-305-02|Escalation PAD-305-02]] — owner decision
2026-09-04, **Variant B**: the `delivery_events.source_attempt_id` FK is the
DATA-107 contract and stays; the live path is brought up to the contract
instead of the contract being lowered to the live path.

## Goal

Make the canonical `captures` / `transcription_attempts` / `representations`
tables the **live** write path of a dictation, so that a finished transcript
has a real `attempt_id` at the moment it is delivered — and the already-built
delivery audit becomes reachable in production.

## Problem

`insert_capture`, `insert_attempt`, `complete_attempt` and `mark_canonical`
were delivered by DATA-105 at repository level and have **no production
caller**. The live path in `actions.rs` writes only the legacy
`transcription_history` row via `managers/history.rs::save_entry`, so at the
delivery call site (`actions.rs:827`) no `attempt_id` exists in scope or in
the database. `delivery_events` therefore stays empty in production while
`SqliteDeliveryAudit` and `deliver_with_audit` are fully tested.

## Scope

- Write the canonical rows on the live dictation path, in this order:
  `insert_capture` (after the WAV is on disk, carrying `audio_file_name`,
  `audio_sha256`, `audio_size_bytes`) → `insert_attempt` → the engine runs →
  `complete_attempt` with `normalized_stt` (or `error`) → `mark_canonical`
  for the first successful attempt.
- Persist post-processed output as a `representation` of that attempt rather
  than as a second transcript, so `engine_raw` stays immutable (STT-103 /
  DATA-105 contract).
- Build a `DeliverySource` from the resulting ids at the delivery call site
  and switch `sink.deliver(&final_text)` →
  `deliver_with_audit(sink, audit, source, &final_text)`. This is the
  call-site change PAD-305 designed the seam for; the sinks themselves do
  not change.
- The failure branch (transcription error) must also produce a terminal
  attempt — `complete_attempt` with `error` — so a failed dictation is
  representable and diagnosable.
- Keep `save_entry` writing the legacy history row in the same flow.
  Dual-write is deliberate: the legacy history UI is not part of this ticket
  and must not regress.

## Out of scope

- migrating or removing the legacy `transcription_history` table;
- history UI changes (HIST-107 / HIST-231 own that);
- schema changes to `captures`, `transcription_attempts`,
  `representations` or `delivery_events` — all four are frozen;
- retry/re-transcription UX (a second attempt per capture);
- architecture redesign beyond wiring the existing repository functions;
- dependency additions;
- unrelated cleanup.

## Acceptance criteria

- [ ] a completed live dictation writes exactly one `capture` row, one
      `transcription_attempt` row in a terminal `success` state, and marks
      that attempt canonical
- [ ] the post-processed text is stored as a `representation` of that
      attempt; `engine_raw` / `normalized_stt` remain byte-identical to what
      the engine produced
- [ ] a **failed** transcription writes a capture plus an attempt in
      terminal `failed` state carrying the error; no canonical attempt
- [ ] delivery goes through `deliver_with_audit`, so every live delivery —
      success **and** failure — appends exactly one `delivery_event` whose
      `source_attempt_id` resolves to the attempt written above
- [ ] the legacy `transcription_history` entry is still written with
      unchanged content and unchanged `history-updated` event behaviour
- [ ] a cancelled dictation writes no delivery event
- [ ] `delivery_events` is non-empty in production after one dictation —
      the accepted debt from G2/G3 is paid

## Required tests/evidence

- [ ] integration test: dictation success → capture + canonical attempt +
      representation + exactly one delivery event, ids consistent
- [ ] integration test: transcription failure → terminal failed attempt, no
      canonical attempt
- [ ] integration test: delivery failure → delivery event with failure
      outcome (DATA-107 requires the event, PAD-305-01)
- [ ] regression test: legacy history entry unchanged (content + event)
- [ ] Windows native smoke: one real dictation, then assert
      `SELECT COUNT(*) FROM delivery_events > 0`
