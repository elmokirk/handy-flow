# Escalation — `NOTE-304-01`

**Category:** ARCH
**Severity:** E1
**Status:** RESOLVED
**Blocks:** ticket

## Problem / Decision

NOTE-304 declares `allowed_paths` of `src-tauri/src/managers/notes.rs`,
`src/components/scratchpad/**`, `src-tauri/tests/note_search/**`, `tests/**`.
Delivering note search required edits outside that set:

| File | Status vs. ticket | Why it was needed |
|---|---|---|
| `src-tauri/src/storage/repositories/search.rs` | not in allowed_paths | owns `search_fts`; notes are the third indexed source |
| `src-tauri/src/storage/repositories/notes.rs` | not in allowed_paths | only SQL owner for notes; keeps the FTS doc in sync in-transaction |
| `src-tauri/src/commands/notes.rs` | not in allowed_paths | `notes_search` command exposure |
| `src-tauri/src/lib.rs` | **forbidden** | command registration |
| `src/bindings.ts` | **forbidden** | tauri-specta regenerates it from the command list |
| `src/i18n/**` | **forbidden** | three new `scratchpad.search*` keys |
| `src/scratchpad/**`, `src/hooks/useScratchpad.ts` | not in allowed_paths | the pad does not live at the catalog's assumed path |

## Evidence

- `planning/04-DATA_PERSISTENCE.md:82` freezes the index contents:
  "Index `normalized_stt`, representations **and active notes**." HIST-231
  delivered only the first two, so the notes half of the frozen contract was
  still open and necessarily lands here.
- The same line requires that "canonical repository write transactions update
  the corresponding FTS document in the same transaction". The only SQL owner
  for notes is `storage/repositories/notes.rs`, so the sync code cannot live
  anywhere else without breaking the single-writer rule stated in that file's
  own header.
- `src/bindings.ts` is generated, never hand-edited. It regenerates from
  `collect_commands!` in `lib.rs`, so exposing any command necessarily
  touches both forbidden files.

## Exact blocked task

NOTE-304 acceptance criterion "search bounded" — there is no way to search
notes without indexing them, and no way to index them without the search and
notes repositories.

## Variant A

**Approach:** Implement the FTS sync in its proper owners (`search.rs` owns
`search_fts` SQL, `notes.rs` owns note SQL and calls into it), and log the
boundary crossing.
**Pros:** Keeps single ownership per table; satisfies the frozen
same-transaction requirement; `rebuild_search_index` stays the one recovery
path for all three sources.
**Cons:** Crosses the ticket's declared paths.

## Variant B

**Approach:** Put note-search SQL in `managers/notes.rs` to stay inside
`allowed_paths`.
**Pros:** No boundary crossing.
**Cons:** Puts raw SQL in the manager layer, which every other feature keeps
in repositories; creates a second writer for `search_fts` behind the FTS
owner's back; the manager cannot join the caller's transaction, so the index
would be updated *after* commit and could silently diverge on crash.

## Recommendation

Choose **A**. Variant B would buy path compliance by breaking two stronger
invariants — single SQL owner per table and same-transaction index updates —
and would leave a durability hole exactly where the contract demands there be
none.

## Affected contracts/files

- `storage/repositories/search.rs` — adds `REF_NOTE`, note document
  upsert/delete, notes branch in `rebuild_search_index`, shared
  `to_match_expr`.
- `storage/repositories/notes.rs` — in-transaction FTS sync on create,
  append, title change, trash and restore; `search_notes`.
- `managers/notes.rs` — `search()` and `get()`.
- `commands/notes.rs`, `lib.rs`, `src/bindings.ts` — `notes_search` exposure.
- `src/scratchpad/ScratchpadWindow.tsx`, `src/hooks/useScratchpad.ts` — search
  panel and `openNote`.
- `src/i18n/**` — `scratchpad.search`, `.searchPlaceholder`, `.searchEmpty`.

## Can independent work continue?

Yes.

## Owner decision

**Accepted Variant A**, consistent with the precedent set in
[[escalations/PAD-303-01|PAD-303-01]]: additive, mechanical shared-file edits
are made by the feature agent and logged for the gate review.

Note for the Orchestrator: the stale scratchpad path called out in PAD-303-01
also affects NOTE-304's `allowed_paths` (`src/components/scratchpad/**`).
Correcting it to `src/scratchpad/**` removes most of this ticket's apparent
boundary crossings.
