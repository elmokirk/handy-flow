# Escalation — `PAD-305-01`

**Category:** DATA
**Severity:** E1
**Status:** RESOLVED
**Blocks:** nothing (ticket corrected, work continued)

## Problem / Decision

PAD-305 acceptance criterion 3 was written as:

> every successful delivery records exactly one delivery event naming the
> correct destination; **no event on failure**

That clause contradicts the frozen delivery-audit contract. Implementing the
ticket literally would have made failed deliveries invisible.

## Evidence

- `planning/tickets/DATA-107.md` acceptance: *"a failed delivery can be
  diagnosed without mutating source"*, with a listed test for a failed
  paste/delivery.
- `src-tauri/src/storage/repositories/deliveries.rs:1-7` (frozen module
  header): *"Failed deliveries are recorded too so they can be diagnosed
  without mutating any source."*
- `NewDeliveryEvent` carries `success: bool` and `error: Option<String>`
  (`deliveries.rs:24-25`). Both fields are unusable under "no event on
  failure" — the schema itself documents the intended semantics.
- The `delivery_events` table is append-only, and DATA-107 requires that
  *"retries create new events rather than overwrite"*, which only makes
  sense if the first (failed) attempt was recorded.

The wrong clause originates from PAD-305 being drafted as a split-out of
PAD-303 (see [[escalations/PAD-303-02|PAD-303-02]]) without re-reading
DATA-107.

## Variants

**A — implement the ticket as written (no event on failure).**
Consistent with the ticket, inconsistent with the frozen contract and with
the existing schema. Would leave `success`/`error` permanently dead and make
delivery failures undiagnosable.

**B — correct the ticket to match DATA-107 (one event either way).**
The ticket is the newer, lower-authority document; DATA-107 is frozen and
its schema is already migrated. Requires editing the acceptance criterion.

## Recommendation

**Variant B.** A ticket may narrow a frozen contract, never contradict it.
The delivered code records exactly one event per delivery attempt, success
or failure, and retries append.

## Trade-offs

Variant B writes an event on every failed paste, so a persistently failing
target produces one row per attempt. That is intended (retry history is the
diagnostic signal) and bounded by the retention work in DATA-108.

## Affected files

- `src-tauri/src/delivery/mod.rs` (`deliver_with_audit`)
- `src-tauri/tests/delivery/delivery_routing_test.rs` (fixtures 04, 06)

## Can work continue?

Yes — resolved in place; the tests were written to the DATA-107 semantics.
