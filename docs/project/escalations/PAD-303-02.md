# Escalation — `PAD-303-02`

**Category:** ARCH
**Severity:** E2
**Status:** RESOLVED
**Blocks:** ticket

## Problem / Decision

PAD-303 acceptance criterion 1 is "dictation target works" — routing dictated
speech into the scratchpad instead of the focused app. Implementing this
inside a scratchpad-owned ticket forces scratchpad-specific branching into
the shared transcription delivery path, which is neither owned by nor
reviewable under PAD-303.

## Evidence

- `DeliveryDestination { FocusedApp, Scratchpad, Clipboard }` already exists at
  `src-tauri/src/storage/models.rs:103` with an `as_str()` mapping.
- `storage/repositories/deliveries.rs:43` exposes `record_delivery`, and the
  module header states "Every successful paste/scratchpad delivery records ONE
  event naming the destination."
- **Neither is called from any production code path.** `grep` for
  `DeliveryDestination::FocusedApp` and `record_delivery` across `src-tauri/src`
  returns only their own definitions. The destination model was specified in an
  earlier phase but the routing seam was never built.
- The only real delivery site is `clipboard.rs:805` (`try_reliable_paste`),
  which is not in PAD-303's `allowed_paths`.
- `src-tauri/tests/scratchpad/pad_transforms_test.rs::fixture_03` exercises
  `notes.save_content(..., SOURCE_DICTATION)` — the persistence layer only.
  It proves a dictation-sourced version can be stored; it does **not** prove
  any transcript ever reaches the scratchpad. The criterion is unmet.

## Exact blocked task

PAD-303 acceptance criterion "dictation target works" and its
"Windows native smoke" evidence requirement.

## Variant A

**Approach:** Branch inside `clipboard.rs` — if the scratchpad is the active
target, call `NotesManager::save_content` instead of pasting.
**Pros:** Smallest diff; closes the criterion inside PAD-303.
**Cons:** Inverts the dependency — the shared delivery path gains a hard
compile-time edge to the notes feature. Every future destination (KB capture
in Phase 4, REST/MCP delivery in Phase 5) adds another branch to the same
function. Leaves `DeliveryDestination` and `record_delivery` dead. Puts
cross-cutting code under a feature agent's ownership with no gate coverage.

## Variant B

**Approach:** Split dictation routing into its own ticket that builds the
delivery seam the frozen model already implies: resolve a `DeliveryDestination`
once, dispatch through a `DeliverySink` abstraction, and record one delivery
event per successful delivery. The scratchpad becomes one sink implementation
among several. Land PAD-303 as transforms-only.
**Pros:** Dependency points the right way — sinks depend on the delivery
contract, not the delivery path on features. Finally wires the dormant
`DeliveryDestination` + `record_delivery` pair, giving an auditable record of
where every transcript went (an enterprise requirement, not a nicety).
Phase 4 KB capture and Phase 5 REST/MCP delivery become new sinks rather than
new branches. Each sink is unit-testable against the trait without a live
paste path.
**Cons:** Larger up-front change; defers the criterion past the G3 gate.

## Recommendation

Choose **B**. Variant A optimises for closing one checkbox and would make the
next three destinations progressively harder to add. The destination enum and
the delivery-event repository were specified precisely so that routing would
be a first-class concern; wiring the scratchpad in as a special case would
strand that design permanently and bury a cross-cutting concern inside a
feature ticket.

Proposed shape for the new ticket:

- `DeliverySink` trait — `fn deliver(&self, text: &str) -> Result<(), DeliveryError>`
  plus `fn destination(&self) -> DeliveryDestination`.
- Implementations: `FocusedAppSink` (wraps today's `try_reliable_paste`),
  `ScratchpadSink` (appends a `SOURCE_DICTATION` note version),
  `ClipboardSink`.
- A resolver that picks the sink from settings/active-target state, and a
  single call to `record_delivery` on success.
- `clipboard.rs` keeps only the focused-app mechanics; it stops deciding
  *where* text goes.

This is additive: `FocusedAppSink` preserves current behaviour exactly, so the
refactor can land and be verified before any new destination is enabled.

## Affected contracts/files

- `src-tauri/src/clipboard.rs` — extract paste mechanics behind a sink.
- `src-tauri/src/storage/models.rs` — `DeliveryDestination` (already frozen).
- `src-tauri/src/storage/repositories/deliveries.rs` — `record_delivery` wiring.
- `src-tauri/src/managers/notes.rs` — `ScratchpadSink` backing call.
- `TICKET_CATALOG.json#PAD-303.acceptance` — criterion 1 moves out.

Yes. PAD-303's transform criteria are complete and independently verifiable.
