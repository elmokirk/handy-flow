# Escalation — `PAD-305-02`

**Category:** ARCH
**Severity:** E2
**Status:** RESOLVED — **Variant B** decided by the owner on 2026-09-04
**Blocks:** one acceptance criterion of PAD-305 (audit in production); the
routing itself is delivered and in use.

## Decision (2026-09-04)

**Variant B.** The FK stays as it is; the audit is wired once the canonical
capture/attempt pipeline is the live write path. Follow-up ticket
[[planning/tickets/PAD-306|PAD-306]] is registered in the catalog and is a
hard dependency of [[planning/tickets/KB-401|KB-401]], so Phase 4 cannot
start before the debt is paid.

## Problem / Decision

PAD-305 requires "every delivery records exactly one delivery event". A
delivery event cannot be written for a live dictation, because the live
transcription path never creates the rows the event is required to point at.

## Evidence

- `src-tauri/src/storage/migrations.rs:220-221`:
  `source_attempt_id TEXT NOT NULL REFERENCES transcription_attempts(id)`.
  A delivery event without an attempt is not representable.
- The live path saves through `managers/history.rs::save_entry` (the legacy
  history table). `insert_capture` and the canonical attempt writer have **no
  production caller** — DATA-105 delivered them at repository level only.
- Consequence: at `actions.rs`, where delivery now happens, there is no
  `attempt_id` in scope and none exists in the database.

So the audit is fully implemented and tested (`SqliteDeliveryAudit`,
8 fixtures with seeded captures/attempts), but is not reachable from the
live dictation flow. Wiring it requires making the canonical
capture/attempt pipeline the live write path — upstream Integrator work
outside this ticket's ownership (`transcript delivery path`).

## Variants

**A — relax the FK / allow attempt-less delivery events.**
Delivery audit works immediately for live dictations. But it breaks the
DATA-107 invariant that every delivered text names its immutable source; an
event that cannot be traced back to an attempt has little diagnostic value,
and the schema change would need a migration on a frozen table.

**B — keep the contract; wire the audit when the canonical pipeline goes
live.** PAD-305 ships the routing seam plus a tested audit port. A follow-up
Integrator ticket makes `insert_capture`/attempt writes the live path and
passes the resulting `DeliverySource` into `deliver_with_audit`. Delivery
events for live dictations start appearing at that point.

## Recommendation

**Variant B.** The FK is the contract; loosening it to make an observer fire
earlier trades a permanent data-integrity guarantee for temporary coverage.
The seam is built so that the follow-up is a call-site change
(`sink.deliver(text)` → `deliver_with_audit(sink, audit, source, text)`),
not a redesign.

Follow-up ticket: **[[planning/tickets/PAD-306|PAD-306]] — canonical
capture/attempt pipeline in the live transcription path** (Phase 4, gate G4,
owner Integrator, depends on DATA-105 / PAD-305). Registered and scheduled
**before** KB-401.

## Trade-offs

Until that ticket lands, `delivery_events` stays empty in production and the
audit is covered by tests only. Nothing regresses: today there is no audit
at all, and the legacy history entry is still written as before.

## Affected files

- `src-tauri/src/actions.rs` (delivery call site; routes, does not audit)
- `src-tauri/src/delivery/mod.rs` (`deliver_with_audit`, `SqliteDeliveryAudit`)
- `src-tauri/src/managers/history.rs` (legacy write path, unchanged)
- `src-tauri/src/storage/repositories/captures.rs` (unused in production)

## Can work continue?

Yes. PAD-305's routing criteria are met and gated; only the production
reachability of the audit is deferred and must be acknowledged at G3.
